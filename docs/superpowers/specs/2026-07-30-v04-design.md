# v0.4: bug fixes and tappable notifications — Design

Drafted 2026-07-30 while v0.3.1 was finishing. **Not yet approved** — the
section marked "Needs your decision" has open questions.

## Scope recommendation: split what the backlog calls "v0.4"

`docs/BACKLOG.md` currently lumps four things under v0.4: the two known bugs,
tappable notifications, the map becoming the home for everything location-based,
and a home-screen widget. That is too much for one release, and it makes the
small urgent things wait behind the large uncertain ones.

Proposed split:

| Release | Contents | Why here |
|---|---|---|
| **v0.4** | The two bugs + tappable notifications | Fully diagnosed or already designed. No new decisions needed. |
| **v0.5** | The map as the home for location actions | Needs real interaction design — see the open questions below. |
| **later** | Home-screen widget | Wants the map work settled first, and is a genuine new surface. |

This spec covers **v0.4 only**. The bugs are the reason: one of them fires a
failure notification every time Wasil parks while already holding the permit,
and that should not wait for a map redesign.

## Part 1: the two bugs

### Bug 1 — claim retries forever when the permit is already yours

Reported from real use on 2026-07-29: switching works once, but parking again
while the permit is already on your own plate produces a constant failure
notification and endless retries.

Cause, confirmed by reading the code:
`PermitRepository.switchTo()` calls `api.activate(vrn)` unconditionally. When
that plate already holds the session, the API rejects the call,
`ClaimPermit.claim()` catches the exception and returns `ParkOutcome.SwitchFailed`,
and `ClaimPermitWorker` maps that to `Result.retry()`. WorkManager then retries
on exponential backoff indefinitely, notifying on every attempt.

Fix: make `switchTo` **idempotent**. Read the active plate first; if it already
equals the target, return `Confirmed(vrn)` immediately without calling activate.

This costs one extra GET per switch. Acceptable — `activePlate()` is already
called immediately afterwards for read-after-write verification, so the shape of
the method does not change, only the early exit.

Tests: target already active returns `Confirmed` and `activate` is never called;
target not active still activates and verifies; a genuine mismatch still returns
`Mismatch`.

### Bug 2 — no cap on claim retries

`ClaimPermitWorker` returns `Result.retry()` for any `SwitchFailed`, with no
attempt limit. Any persistent failure — wrong credentials, an API change — loops
forever, notifying each time.

Fix: give up after five attempts using `runAttemptCount`, with one final
notification saying retries have stopped and the permit was not changed. Silence
after a give-up would be worse than the loop: the user must know the permit did
not move.

Test: the fifth attempt returns failure rather than retry, and the give-up
notification fires exactly once.

## Part 2: tappable notifications

Approved in review on 2026-07-30, cut from v0.3.1 because it needs a
`PendingIntent`, a screen and ViewModel state rather than being pure layout.

Every notification gains a content intent, so tapping it opens the app to a
full-screen version of the same decision instead of only offering the cramped
notification actions.

The blocked-claim case matters most, and is the one worth designing carefully:
the Handoff mark with the dot mid-travel, the facts (when the other car parked,
when it was last heard from, why claiming is risky), and the same three choices
the notification offers — claim anyway, mark this spot free, leave it.

The other notifications reuse the same screen with their own text and actions:
the manual-decision prompt, the give-back prompt, and the takeover alert.

**Notification small icons become state-aware** — the mark with the correct arc
lit — which v0.3.1 deliberately left as a single static drawable.

### Architecture

A decision must survive the app being killed between the notification firing and
the user tapping it, so it cannot live in memory:

- The pending decision is written to the existing `ParkStateStore` as a small
  record (which decision, its facts, when it was raised).
- The `PendingIntent` carries only an identifier; the screen reads the record.
  Never put the facts in intent extras — they go stale and a killed process
  loses them anyway.
- A decision is cleared when acted on, when it expires, or when the situation
  that raised it no longer holds (the other car drove off).
- The screen and the notification actions call **the same** handlers, so there is
  exactly one implementation of "claim anyway" regardless of entry point.

This is the first release where `ParkStateStore` gains fields since v0.3.1's
freeze on behaviour, which is precisely why it is a minor bump and not a patch.

### Testing

The decision record's lifecycle is pure logic and gets real tests: raising,
clearing on action, clearing when conditions lapse, expiry, and that a stale
record never resurfaces. The screen itself reads that state and draws.

## Needs your decision — v0.5, the map

Not in scope here, recorded so the questions are not lost. None of these have an
obvious right answer and I should not pick for you:

1. **Drawing a free zone.** Tap a point and drag a radius, or tap to drop a pin
   and set the radius with a slider? Dragging is fewer steps; a slider is far
   easier to hit precisely on a phone while standing in the street.
2. **Selecting a tariff area.** Tap the polygon on the map, pick the code from a
   list, or type it? Tapping is the most natural, but Amsterdam's areas are
   neighbourhood-sized and overlap at edges, so a mis-tap is easy and its
   consequence is a wrong rate shown.
3. **Correcting the parked pin.** Should dragging the car's pin also update the
   shared state the other phone reads, or only your own view? Updating shared
   state means a mis-drag can wrongly unblock or block your brother.
4. **Home zone editing.** The radius slider already exists in Settings. Does it
   move to the map entirely, or live in both places?

Each answer changes the implementation materially, so v0.5 gets its own
brainstorming pass rather than being guessed at here.
